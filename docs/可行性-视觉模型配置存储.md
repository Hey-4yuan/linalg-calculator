# 可行性分析：网页端保存视觉模型配置

结论先行：**技术上完全可行，而且已经实现了**——配置写在 `localStorage`，键名带应用前缀，读写全程 try/catch 包裹。
真正需要判断的不是"能不能存"，而是**"存成什么样、在哪些场景会丢、被谁看到"**。本文给出选型对比、威胁模型和一份分优先级的改造清单。

---

## 1. 现状：现在是怎么存的

| 项目 | 实现 |
|---|---|
| 存储介质 | `localStorage`（同步、字符串键值） |
| 键名 | `__miaoda_<appId>__:` + `__app_linalg_ocr_config` |
| 值 | JSON：`{"baseUrl":"…","apiKey":"sk-…","model":"gpt-4o-mini"}` **明文** |
| 写入 | 点「保存配置」时整体覆盖；三项 trim 后存 |
| 读取 | 弹窗打开时回填；识别前再读一次，缺字段直接报「OCR 配置不完整」 |
| 清除 | 「清除配置」立即执行，无二次确认 |
| 异常处理 | 读写失败只 `console.error`，界面无提示（满配额/隐私模式时可能"看起来保存了，其实没存"） |
| 隔离粒度 | 同源 + 同浏览器 profile + 同设备；**不随浏览器账号同步** |

顺带确认两件已做的事：API Key 输入框是 `type="password"`（不明文回显）、界面明确写了"仅保存在浏览器本地，不会上传到任何第三方"。

## 2. 技术可行性的四条硬约束

| 约束 | 具体表现 | 对本项目的影响 |
|---|---|---|
| **同源隔离** | `file://`、`http://127.0.0.1`、`https://你的域名` 是三个不同的源 | 把 HTML 换个路径/换个打开方式，配置就"消失"（不是丢了，是读不到另一个源的库） |
| **容量** | 通常 5 MB 级/源，够存几十万条这样的配置 | 不是问题 |
| **生命周期** | 用户清缓存、隐私模式、浏览器重装、Safari 的 7 天规则都会清掉 | 需要"配置可迁移"（导出/导入），否则每次重配 Key |
| **不跨设备** | 浏览器不同步 `localStorage` | 换手机/换电脑必须重填 |

### 2.1 Safari / iOS 的关键细节（容易踩）

- Safari 的 ITP 会删除**脚本可写存储**（`localStorage`、`IndexedDB`、Service Worker 缓存等）在「7 个 Safari 使用日无交互」之后；
- **豁免**：添加到主屏幕的 Web App 使用独立存储桶，其一级域名不受这个 7 天上限约束；
- 结论：**在 iPhone 上用 Safari 标签页打开网页版 → 一周不用就要重配 Key；添加到主屏幕后不会。** 这条直接影响 iOS 端的形态选择（见《可行性-iOS端.md》）。

### 2.2 `file://` 的两个不确定性

- 有的浏览器把每个本地文件当独立源，有的把整个 `file://` 当一个源——跨浏览器不一致，**同一份 HTML 换个文件名可能就读不到旧配置**；
- `crypto.subtle`（Web Crypto）在部分浏览器的非安全上下文里不可用。所以**任何加密方案都必须先判断 `window.isSecureContext`**，不能假设 `file://` 一定有。

## 3. 存储方案对比

| 方案 | 容量 | 持久性 | 加密 | 跨设备 | 实现成本 | 适用 |
|---|---|---|---|---|---|---|
| **localStorage（现状）** | ~5 MB | 中（可被清） | 无 | ❌ | 已实现 | 个人机、单人使用 |
| sessionStorage | ~5 MB | 关标签即失 | 无 | ❌ | 低 | 公用电脑、临时演示 |
| IndexedDB | 大（按磁盘配额） | 中 | 无 | ❌ | 中 | 需要存多套配置/历史 |
| Cookie（`document.cookie`） | 4 KB | 中；ITP 对其也有 7 天限制 | 无；**不能设 HttpOnly** | ❌ | 低 | 无优势，不推荐 |
| **Web Crypto + 口令加密后存 localStorage** | ~5 MB | 中 | ✅ AES-GCM（口令派生） | ❌ | 中 | 有他人共用设备的风险 |
| Credential Management API（存进浏览器密码管理器） | — | 由密码管理器决定 | ✅ 系统级 | 随浏览器账号同步（若开启） | 中 | Chrome/Edge；Safari 支持有限 |
| Capacitor Keychain / Keystore（原生壳） | — | 高 | ✅ 系统钥匙串 | ❌ | 中（需原生插件） | APK / 未来的 iOS 壳 |
| 服务端代理（云函数持有 Key） | — | 高 | ✅（Key 不下发） | ✅ | 高（要后端 + 限额 + 鉴权） | 要给别人用、或要求"打开即用" |

一句话：**明文 `localStorage` 是"够用且诚实"的方案**；要更强只有两条路——本机加密（提高门槛，不解决"同机他人已登录"）或服务端代理（真正把 Key 从客户端拿掉）。

## 4. 威胁模型：谁可能看到这个 Key

| 威胁 | 现实可行性 | 现状 | 缓解 |
|---|---|---|---|
| 同一台电脑的其他人打开浏览器 | **高**（F12 → Application → Local Storage，5 秒） | 无防护 | 口令加密 / 系统钥匙串 / 用独立浏览器 profile |
| 恶意浏览器扩展读所有站点存储 | 中 | 无防护 | 减少装扩展；或用独立 profile |
| 页面被注入脚本（XSS） | 低（无用户 HTML 注入、无第三方脚本；仅字体 CSS 从 CDN 加载） | 无防护 | 保持不引入外部脚本；CSP 可选 |
| 屏幕共享/录屏时打开配置弹窗 | 中 | Key 是 password 框，默认打码 | 演示时别打开弹窗；或加"显示/隐藏"控制 |
| 把 HTML 文件发给别人 | 低 | Key 不在文件里 | 保持"配置不入包" |
| 浏览器备份/迁移工具 | 低-中 | 随 profile 一起被复制 | 口令加密 |
| 服务商侧日志 | 取决于服务商 | Key 随请求头发给对方 | 选可信服务商；定期轮换；设置额度上限 |
| Key 泄露后的损失 | — | 无限额 | 在服务商后台**设消费上限**、定期轮换；泄露后立即吊销 |

**要明确的一点**：把 Key 硬编码进 HTML 再分发，等于公开。任何"下载即用、不用配置"的方案，都必须是**服务端代理 + 鉴权 + 限额**，不存在纯前端的优雅解。

## 5. 建议方案（按投入分级）

### P0：不改架构，只补三个缺口（半天）

1. **保存失败要能看见**：`localStorage` 抛异常（配额满、隐私模式）时，现在只写 console。改成界面提示「配置未能保存（浏览器禁止本地存储）」。
2. **清除配置加二次确认**：误点一次就要重填 Key，成本不对等。
3. **导出 / 导入配置**：一段 JSON 文本（或二维码），换设备时不用重新申请。
   ```js
   // 导出（不含提示信息，纯配置）
   const cfg = JSON.parse(localStorage.getItem(KEY) || '{}');
   const text = JSON.stringify(cfg, null, 2);
   // 导入：校验字段齐全 + 类型正确后再写，避免写进脏数据
   ```

### P1：加一层口令加密（1 天）

适用：电脑可能被他人使用，但不想上后端。

```js
// 概念示意：PBKDF2 派生密钥 → AES-GCM 加密 → 存密文
async function seal(plain, pass) {
  if (!window.isSecureContext) throw new Error('当前环境不支持加密存储');
  const enc = new TextEncoder();
  const salt = crypto.getRandomValues(new Uint8Array(16));
  const iv   = crypto.getRandomValues(new Uint8Array(12));
  const base = await crypto.subtle.importKey('raw', enc.encode(pass), 'PBKDF2', false, ['deriveKey']);
  const key  = await crypto.subtle.deriveKey(
    { name: 'PBKDF2', salt, iterations: 310000, hash: 'SHA-256' },
    base, { name: 'AES-GCM', length: 256 }, false, ['encrypt']
  );
  const ct = await crypto.subtle.encrypt({ name: 'AES-GCM', iv }, key, enc.encode(plain));
  return { v: 1, salt: [...salt], iv: [...iv], ct: [...new Uint8Array(ct)] };
}
```

要点：

- 口令**不落盘**，只在解锁时输入；忘记口令 = 配置作废（要能接受）；
- 每次唤醒需解密（弹窗打开时），别把明文缓存在内存全局变量里长期驻留；
- `file://` 下若 `crypto.subtle` 不可用，退化为要么不加密、要么要求用 https/localhost 打开。

### P2：把 Key 移出客户端（1–2 天，需后端）

```

前端 → 你的云函数（带一次性/短期 token） → 模型服务商（Key 在服务端环境变量）
```

- 前端只存"会话票据"，泄露也只能用很短时间；
- 可在服务端加**每日次数/额度上限**、按用户限流；
- 适合"要发给同学用"的场景——否则每个人都得自己申请 Key，这是当前最大的使用门槛。

### 不建议做的

| 做法 | 为什么不做 |
|---|---|
| Base64 / 自定义异或"混淆"后存 | 只是拖延 10 秒，反而给人"已加密"的错觉 |
| 把 Key 写进 HTML | 等于公开分发密钥 |
| 把 Key 存 Cookie | 4 KB 限制、无 HttpOnly、仍受 ITP，越改越差 |
| 存到 URL 参数里 | 会进历史记录、Referer、截图，泄露面更大 |

## 6. 结论

| 问题 | 回答 |
|---|---|
| 网页端能保存视觉模型配置吗？ | **能**，且已在用；`localStorage` 是本场景的合理选择 |
| 安全吗？ | 对"个人设备、单人使用"够用；对"共用设备/多人分发"不够 |
| 会丢吗？ | 会。清缓存、隐私模式、换源、换设备、Safari 7 天规则都会导致丢失 |
| 最该先补什么？ | **导出/导入**（解决"丢一次就要重新申请 Key"的痛点）+ 保存失败提示 |
| 想彻底解决分发问题？ | 上服务端代理，Key 不下发；纯前端做不到 |
