## 1. 一句话结论

这是一个**标准 Vite + React 19 + TypeScript 单页应用**，业务代码只有 6 个库文件 + 5 个页面区块，约 3000 行；
所谓"妙搭外壳"并不是什么黑盒，它来自两个 npm 依赖：`@lark-apaas/client-toolkit-lite`（存储、日志、错误边界、polyfill）和 `@lark-apaas/coding-preset-vite-react`（构建预设）。

**源码可读、可改、可本地构建**，此前"必须回平台改"的结论已作废。

### 4.3 状态管理

没有 Redux/Zustand，也没有全局 store：

- 页面级状态在 `HomePage`（当前 Tab、分数模式）；
- 各区块自己 `useState` 管理矩阵/结果，切 Tab 不卸载（`TabsContent` 保持挂载），所以数据不会丢；
- 唯一持久化：`scopedStorage`（平台封装的 localStorage），键 `__app_linalg_fraction_mode` 与 `__app_linalg_ocr_config`。

## 5. 三条数据流

**① 数值矩阵运算**

```
MatrixGrid（输入字符串）
  └─ Fraction.safeParse → FMatrix（Fraction[][]）
       └─ SingleMatrixSection 的事件处理 → matrix-ops
            ├─ rref / determinant / inverse / eigenvalues / matrixPower
            └─ 返回 { 结果, steps }
                 └─ MatrixDisplay / StepsAccordion（按 fractionMode 渲染）
```

**② 符号运算**：`SymbolicMatrixSection` 自己维护字符串矩阵 → `symbolic.ts` 解析成表达式树 → 化简 → `SymbolicMatrixDisplay` 渲染。

**③ OCR**

```
OCRUploadButton（未配置→弹设置；已配置→选文件）
  └─ ImageEditorDialog（旋转/翻转/裁剪 → canvas → JPEG）
       └─ ocr-service.recognizeMatrixFromImage(file, mode)
            ├─ getOCRConfig()：scopedStorage 读取
            ├─ POST {baseUrl}/chat/completions（temperature 0，45s 超时）
            └─ 校验 rows/cols/data → OCRMatrixResult
                 └─ safeOcrResultToFMatrix：逐格 safeParse，失败置 0 并回报 failedCells
                      └─ 回填输入网格 + toast 提示
```

## 6. 构建链路：一份源码，三种产物

```
npm run build            → dist/client          （平台部署用，含 routes.json / polyfills / 字体重写）
node scripts/make-standalone.mjs → dist-standalone（纯净离线站，只保留 4 类业务 chunk）
node scripts/make-single-file.mjs → 线性代数计算器.html（单文件，双击可用）
```

三者关系与差异：

| 产物 | 入口 | 资源形态 | 用途 |
|---|---|---|---|
| `dist/client` | `index.html` | 多 chunk + polyfills + `routes.json` | 上传到平台/静态托管 |
| `dist-standalone` | `index.html`（脚本重写） | 只保留 `rolldown-runtime / radix / toolkit / index-` 四类 chunk | 直接当 Capacitor 的 `webDir`，或任意静态服务器 |
| 单文件 HTML | 内联 `<style>` + 内联 `<script type="module">` | esbuild 把 standalone 的入口再 bundle 一次，与 CSS/favicon 一起内联 | 发文件、离线、U 盘 |

**"妙搭"痕迹来源**（此前误判为黑盒）：

- `make-single-file.mjs` 往 HTML 注入 `window.appId / userId / tenantId / __BASENAME__ / _appInfo`；
- `@lark-apaas/client-toolkit-lite` 提供 `AppContainer`、`scopedStorage`（键前缀 `__miaoda_<appId>__:`）、`logger`、埋点；
- `@lark-apaas/coding-preset-vite-react` 把字体 `@import` 重写指向 `https://miaoda.feishu.cn/fonts`。

所以"品牌页脚/埋点"不是业务代码写的，是平台依赖带来的。若要彻底去平台化，需要替换这两个依赖（`scopedStorage` → 原生 `localStorage`，`logger` → `console`，`AppContainer` → 空壳），属于可选改造。

## 7. 读源码纠正的五个误判

| # | 此前的结论（基于产物反推） | 源码事实 | 影响 | 处置 |
|---|---|---|---|---|
| 1 | RREF 取"该列第一个非零行"作主元，只有 det 用整数友好启发式 | **两者用同一套 `pivotFriendliness`**：整数优先（0），否则 `分母 + 0.1×|分子|`，评分 `friendliness×1000 − |值|` | 步骤形态和"为什么 RREF 后分数不难看"的解释完全不同 | 技术手册 5.1 已改写 |
| 2 | 方程组未知数上限 1–9 | `maxCols=11`、未知数按钮上限 **10** | 用户手册/技术手册的"1–9"是错的 | 已改为 1–10 |
| 3 | L7：非法输入静默保留旧值，用户以为改成功 | `MatrixCell` 有 `isInvalid` 状态：解析失败时输入框变红、保持编辑态、不提交 | 这不是缺陷，而是**符合 PRD 的设计** | L7 从缺陷表移除，并说明原因 |
| 4 | L8：`copyToClipboard` 是业务里的死代码 | 业务代码完全没有 clipboard；该函数来自 `@lark-apaas/client-toolkit-lite` | 责任归属不同，且无法通过改业务代码"用上"它 | L8 改为"平台库提供、业务未接复制按钮" |
| 5 | 改功能"必须回妙搭改"，产物只能字节级打补丁 | 源码齐全，`npm i && npm run build:all` 即可重出全部产物 | 开发流程完全变了；字节补丁只作为历史归档 | 开发者指南已重写；v1.2 改用源码构建 |

另外两处小修正：

- 单矩阵/双矩阵最小行数实际是 **1**（PRD 写 2），以代码为准；
- 符号矩阵子 Tab、OCR 模块都不在原始 PRD 里，是后续迭代加的。

## 8. 已做的源码级修复

v1.1 的两处缺陷当时只能在压缩产物上做字节替换，现在改成正式源码修改：

### 8.1 无解时增广矩阵秩错误（原 L13）

`matrix-ops.ts` 原实现：

```ts
const { rref: rrefMat, rank: rankAb, pivotCols, steps } = rref(augmented, 1);
const rankA = pivotCols.length;
```

`rref(augmented, 1)` 只在系数列选主元，返回的 `rank` 恒等于 `rankA`，于是无解分支打印「系数矩阵秩 = 1，增广矩阵秩 = 1，秩不相等」。

修复：

```ts
const { rref: rrefMat, pivotCols, steps } = rref(augmented, 1);
const rankA = pivotCols.length;
// 增广矩阵的秩 = 行最简形中非零行的行数（行变换不改变行空间维数）
const rankAb = rrefMat.reduce((acc, row) => acc + (row.some((v) => !v.isZero()) ? 1 : 0), 0);
```

比"用 `rankA + 1`"更稳：不依赖"无解 ⇒ 秩恰好多 1"的推理，直接算出来。

### 8.2 OCR 无超时（原 L4）

`ocr-service.ts` 原实现直接 `await fetch(...)`，接口挂起就永远转圈。修复：

- 新增常量 `OCR_TIMEOUT_MS = 45_000`；
- 用 `AbortController` + `setTimeout` 控制 `signal`，在 `finally` 里 `clearTimeout`；
- 捕获 `DOMException` 且 `name === "AbortError"` 时抛出「识别超时（45 秒无响应），请检查网络或更换模型接口」。

### 8.3 构建脚本的 Windows 兼容

`make-standalone.mjs` 原本用 `fs.cpSync`。在这台 Windows + Node 22 的环境里，`cpSync` 会**静默崩溃**（进程退出码 127，无任何报错，甚至 `try/catch` 都抓不到）。已改为手写递归复制（`readdirSync` + `copyFileSync`），并加注释说明原因。

## 9. 本地构建与验证

```bash
cd source/linear-algebra-calculator/web-source
npm install                     # 874 个包，约 2–3 分钟（npmmirror）
npm run typecheck               # tsc 类型检查，必须 0 错误
npm run build:all               # vite build → standalone → 单文件
node ../../../tests/build-and-test.mjs   # 18 项求解器断言（直接测源码）
```

**三个必须知道的坑**（都已在本次构建中踩过并解决）：

1. **三个原生可选依赖可能缺失**。`package-lock.json` 在别的平台生成，npm 不会补装 Windows 二进制，表现为 `Cannot find module ...binding-win32-x64-msvc`：

   ```bash
   npm install --no-save \
     @rolldown/binding-win32-x64-msvc@1.2.7 \
     lightningcss-win32-x64-msvc@1.32.0 \
     @tailwindcss/oxide-win32-x64-msvc@4.3.3
   ```

   ⚠️ 必须**一条命令装齐**：`--no-save` 装的东西在下次 `npm install` 时会被当"多余包"删掉。

2. **`fs.cpSync` 在本机会崩**（见 8.3），已修脚本。

3. **路径含中文 + OneDrive** 不影响 Vite，但会让部分脚本行为异常（本次 cpSync 崩溃与此无直接证据，但同类环境建议把仓库放到 `D:\` 等纯 ASCII 路径，可少踩坑）。

**本次构建结果**（2026-10-19）：

| 产物 | 大小 | 校验 |
|---|---|---|
| `dist/client` | 2029 modules，3.81s | 含 `index-BF0G9RKH.js`、`toolkit-DzyLbpaK.js` |
| `dist-standalone` | 1.3 MB | 只保留 1 个 JS + 1 个 CSS 入口 |
| 单文件 HTML | 1,237,144 字节 | `node --check` 通过；界面文案、存储键、OCR 超时、`rankAb` 修复均已确认存在 |

> 单文件从 1.29 MB 降到 1.24 MB：新构建的 CSS 233 KB（原 248 KB），且不再带旧的 map/冗余 chunk。

## 10. 遗留问题与建议

按"改动成本 / 收益"排序：

| # | 问题 | 说明 | 建议 |
|---|---|---|---|
| 1 | 无单元测试框架 | 目前只有 `tests/build-and-test.mjs`（自建断言） | 引入 Vitest，把 `lib/*` 全量覆盖；matrix-ops 是纯函数，成本很低 |
| 2 | 依赖装了 874 个包，业务用不到 10 个 | echarts、recharts、framer-motion、gsap、react-hook-form、zod…都没引用 | 清理 `package.json`，安装体积和审计面都会降下来 |
| 3 | 平台依赖不易替换 | `AppContainer` / `scopedStorage` / `logger` / polyfill 来自 `@lark-apaas/*` | 若要去平台化：写 20 行的 storage/logger 适配层替换即可 |
| 4 | 三阶以上特征值仅实根，且不报"未收敛" | QR 迭代固定 100 次，收敛与否都以对角线返回 | 增加收敛标志；或实现 real Schur 提取 2×2 块处理复根 |
| 5 | 重特征值的特征向量可能重复 | 反幂法对重根收敛到同一方向 | 改用 `rref(A−λI)` 的零空间基 |
| 6 | 死代码 | `determinant` 的 `detScale` 恒为 1；`rref` 的 `maxAbsScore` 未使用；`fraction.pow` 的负指数分支走浮点 | 清理；`pow` 若不使用可删 |
| 7 | 无 PWA manifest / Service Worker | 单文件版靠内联离线，但无法"添加到主屏幕" | 若走 iOS PWA 路线需补（见《可行性-iOS端》） |
| 8 | OCR 配置无导出/导入 | 换设备要重填 Key | 见《可行性-视觉模型配置存储》P0 项 |
