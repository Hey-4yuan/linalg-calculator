## 4. 数值核心：有理数类

### 4.1 表示

```js
class Fraction {
  num;  // 分子，JS number
  den;  // 分母，JS number，恒 > 0
}
```

构造时做两件事：**约分**（`gcd(|num|, den)`）与**符号归一**（负号一律挂在 `num`）。因此 `2/4`、`-1/-2`、`0.5` 都规范化为 `1/2`。`den === 1` 即整数。

### 4.2 解析规则（`from` / `fromString` / `safeParse`）

| 输入 | 结果 | 备注 |
|---|---|---|
| `""` / `"-"` | `0` | 空输入按 0 处理 |
| `"12"` | `12/1` | |
| `"-7"` | `-7/1` | |
| `"3/4"` | `3/4` | 以 `/` 切分，两侧 `parseFloat` 后再规范化 |
| `"-5/2"` | `-5/2` | |
| `"0.25"` | `1/4` | `fromDecimal`：按小数点位数放大成 `25/100` 再约分 |
| `"1/2/3"` | 抛「无效分数」 | 只允许一个 `/` |
| `"1/0"` | 抛「分母不能为 0」 | |
| `"abc"` / `"2a"` | 抛「无效数值」 | 单元格不做表达式解析 |
| `"1e-3"` | `1/1000` | 走 `parseFloat` → 十进制字符串 → 分数 |

安全入口 `safeParse` 捕获异常返回 `null`，视图层据此**保留原值**或**置 0**（OCR 场景），不会让一个坏格子崩掉整个页面。

### 4.3 精度边界

`num`、`den` 是 IEEE-754 double，只有 `|num|`、`den` ≤ 2⁵³ 时运算才严格精确：

- 10×10 的整数矩阵做完 RREF 后，中间量的分子分母通常仍在 10⁶ 量级，安全；
- 但含大整数（如元素是 10 位以上）、或 10 阶分数矩阵做行列式展开时，分子分母会快速膨胀，**可能越过 2⁵³ 而悄悄失去精确性**；
- 这不是可选优化，而是当前实现的硬边界。若要彻底解决，需把 `num/den` 换成 `BigInt`。

### 4.4 运算 API

| 方法 | 说明 |
|---|---|
| `add` / `sub` / `mul` / `div` | 四则运算，结果自动约分 |
| `neg` / `abs` / `reciprocal` | 取负 / 绝对值 / 倒数（零的倒数抛错） |
| `isZero` / `isOne` / `isNegOne` / `isInteger` / `isNegative` / `sign` | 判定与符号 |
| `compare` / `eq` | 交叉相乘比较，避免浮点误差 |
| `toDecimal` | 转浮点（仅显示与特征值路径使用） |
| `toFractionString` | `p/q`；整数输出 `p` |
| `toDecimalString(6)` | 保留 6 位后**去尾零** |
| `toCoeffString` | 系数专用：1 → `""`，−1 → `"-"`（用于步骤描述里 `R1 ← R1 + R2` 这种写法） |

## 5. 算法实现

矩阵统一用**行优先二维数组**表示。分两种元素类型：有理数（数值模式）与符号表达式 AST（符号模式），两者算法结构对称、实现分离。

### 5.1 行最简形 RREF（`rref`）

Gauss-Jordan 消元，主元采用**整数友好策略**（与行列式同一套评分函数）：

```
pivotFriendliness(f) = 0                       若 f 是整数
                     = f.den + |f.num| × 0.1   否则
score(f) = pivotFriendliness(f) × 1000 − |f|

m = 0
for col in 0 .. 系数列数-1:
    在 i ≥ m 的行中，选 score(A[i][col]) 最小的非零元作主元
    if 无主元: continue
    if pivotRow ≠ m: 交换 R_m, R_pivotRow        → step{type:"swap"}
    if A[m][col] ≠ 1:
        整行乘以 1/A[m][col]                     → step{type:"scale"}
    for i in 0..rows-1, i ≠ m:
        if A[i][col] ≠ 0:
            R_i ← R_i − A[i][col]·R_m            → step{type:"add"}
    pivotCols.push(col); m++
return { rref, rank: pivotCols.length, pivotCols, steps }
```

要点：

- **主元不是"第一个非零"，而是"算起来最省事的"**：优先整数主元，其次分母小的；同分时取绝对值大的（数值更稳）。这是为了让消元过程尽量不产生复杂分数——既好看也好核对；
- 归一化只在主元不为 1 时执行（少一步无意义的 `× 1`）；
- **消去所有行**（含上方），一次跑完即得行最简形；
- 步骤只有三种：`swap` / `scale` / `add`，渲染为 `R₂ ← R₂ − 3R₁`（行号用 Unicode 下标）；
- `augmentedCols > 0` 时（方程组、求逆），最后一列/右侧块不参与主元选择，但仍参与行变换——保证「常数列不能当主元」；
- 精确算术下这种主元选择不影响正确性，只影响**步骤最短**与**中间分数规模**。

复杂度 O(min(m,n)·m·n)。源码位置：`src/lib/matrix-ops.ts` 的 `rref()`。

### 5.2 行列式（`determinant`）

同样是「消元到上三角再乘对角」，但**带主元启发式**，目的是压制分数膨胀：

```
for m in 0 .. n-1:
    # 选主元：优先整数（分母为 1），其次分母小、分子小
    pivotScore(S) = 0                        if S 是整数
                  = S.den + |S.num| * 0.1    otherwise
    v = argmin over i ≥ m of ( pivotScore(S) * 1000 − |S| )
    if 该列全零: return det = 0
    if v ≠ m: 交换 → sign = −sign，记录 step
    for i in m+1 .. n-1:
        # 只对下方消元，不做归一化
        倍数 = −A[i][m] / A[m][m]
        R_i ← R_i + 倍数·R_m                 → 记录 step
det = sign · Π A[i][i]
```

关键取舍：

- **不归一化主元行**——避免了除法带来的分母膨胀，最后的 det 由「符号 × 对角乘积」直接得到；
- 主元评分里 `×1000` 让「是否整数」成为最高优先级，`− |S|` 在同类中偏向绝对值大的（数值更稳）；
- 与 RREF 使用**同一套** `pivotFriendliness` 评分（见 5.1），区别只在于 det 不做归一化、只消下方；
- 源码里 `detScale` 变量恒为 `Fraction.ONE`（从未被修改），属于死代码，可删。

### 5.3 逆矩阵（`inverse`）

```
构造 [A | I]（n × 2n）
对前 n 列做 RREF（augmentedOffset = n）
if rank < n: return null   // 奇异，视图层提示「该矩阵不可逆」
return RREF 的右侧 n 列
```

步骤面板展示的正是这个 `[A|I]` 的化简过程。

### 5.4 秩 / 迹 / 转置

| 运算 | 实现 |
|---|---|
| rank | 直接取 `RREF().rank`（主元个数） |
| trace | `Σ A[i][i]`，循环 `min(rows, cols)`（非方阵取较短的主对角） |
| transpose | 行列互换，返回新矩阵，不改原值 |

### 5.5 矩阵幂（`matrixPower`）

```
if 非方阵: 抛「矩阵幂要求方阵」
if n 不是整数: 抛「指数必须为整数」
if n < 0: A⁻¹ 存在则递归求 (A⁻¹)^(−n)，否则抛「负指数要求矩阵可逆」
if n == 0: 返回 I
二进制快速幂：结果 = I; 底 = A
while n > 0: if n 奇数: 结果 = 结果 × 底; 底 = 底 × 底; n >>= 1
```

全程有理数精确运算，10 阶矩阵 30 次幂仍在毫秒级。

### 5.6 特征值与特征向量（`eigenvalues`）

先统一转成浮点（**这是全应用唯一的浮点主路径**），再按阶数分支：

> 入口限制：`SingleMatrixSection` 在调用前判断 `size > 5` → 直接报错，因此实际最多 5 阶。

| 阶数 | 方法 | 说明 |
|---|---|---|
| 1 | 直接取 `A[0][0]` | 特征向量取 `[1]` |
| 2 | 解析解：`λ = (tr ± √(tr² − 4det)) / 2` | 判别式 < 0 时返回 `complexEigenvalues = [{real, imag}, {real, −imag}]`，此时 `eigenvalues` 为空 |
| n ≥ 3 | QR 迭代 | 见下 |

**QR 迭代（`M$`）**：

- 对当前矩阵做 QR 分解（Gram-Schmidt 正交化，遇到近似零列时补标准基向量）；
- `A ← R·Q`，重复至多 **100 次**，判据是下三角部分所有元素绝对值 ≤ **1e-10**；
- 收敛后取对角线作为特征值，**降序排列**。

**特征向量（`fO`）**：对每个 λ 做反幂法/逆迭代——解 `(A − λI)x = b`（部分主元高斯消元 + 回代），归一化后与上一次迭代比较，最多 **50 次**，初值取 `(1/√n, …, 1/√n)`。

> 界面提示：「特征值与特征向量采用数值方法近似计算，结果可能存在微小误差」——用户手册中也强调 3 阶以上只有实特征值。

### 5.7 线性方程组（`solveLinearSystem`）

输入是增广矩阵 `[A|b]`，变量名按 `x1 … xn`（`n = 列数 − 1`）生成。

```
{rref, rank, pivotCols, steps} = RREF([A|b], augmentedOffset = 1)
rankA = |pivotCols|, rankAb = rank

# 1) 矛盾判定：存在「系数全零但常数非零」的行
for each row: if 前 n 列全零 且 常数列非零 → 无解

# 2) 唯一解：rankA == n
if rankA == n: x[i] = rref[i][n]

# 3) 无穷多解：rankA < n
自由变量 = 非主元列对应的变量
特解：主元变量取 rref[行][常数列]，其余为 0
基础解系：对每个自由变量 f
    η[f] = 1
    每个主元行 r：η[pivotCols[r]] = −rref[r][f]
```

返回值结构：

```js
{ type: "unique"   , solution, rankA, rankAb, rref, pivotCols, variableNames, steps }
{ type: "infinite" , freeVariables, particularSolution, basisVectors, rankA, rankAb, ... }
{ type: "no-solution", rankA, rankAb, ... }
```

三个结论分别对应 `rankA = rankAb = n`、`rankA = rankAb < n`、`rankA ≠ rankAb` 三种情形，与线性代数教材判据一致。

> **已修复（源代码修复，v1.2）**：原实现把 `rref(augmented, 1)` 返回的 `rank` 当作 `rankAb`，而该调用的主元只在**系数列**内选取，所以 `rankAb` 恒等于 `rankA`，界面会打印「系数矩阵秩 = 1，增广矩阵秩 = 1，秩不相等」。
> 修复后直接按定义算：`rankAb = 行最简形中非零行的行数`（行变换不改变行空间维数）。
> 无解结论本身一直是对的（由「系数全零但常数非零」的矛盾行判定），错的只是展示值。详见《源码解析》8.1。

### 5.8 符号运算

#### AST 节点

```js
{ type: "num", value }     // 有理数常量
{ type: "var", name }      // 变量，如 "a"、"x1"
{ type: "pi"  }            // 常量 π
+ 二元/一元运算节点（add / sub / mul / div / pow / neg）
```

#### 解析

递归下降 + 词法分析：

- 词法：数字、标识符（连续字母+数字）、运算符 `+ − * / ^`、括号 `( )`；`×` `÷` 视同 `*` `/`；`π` 视同标识符 `pi`；
- 语法：`expr → term (('+'|'-') term)*`，`term → factor (('*'|'/') factor)*`，`factor → base ('^' factor)?`，`base → num | ident | '(' expr ')' | '-' base`；
- 解析结束后若还有剩余 token，报「表达式未完全解析，多余: …」；
- 每次构造节点都会做一次**化简**（合并常数、消去 0/1、合并同类项的最小子集），所以 `a*1` 直接得到 `a`。

#### 各运算

| 运算 | 实现 | 上限 |
|---|---|---|
| det | 1/2/3 阶用显式公式（2 阶 `ad−bc`，3 阶按第一行代数余子式展开），更高阶退化为符号高斯消元 | 3 阶（UI 拦截） |
| inv | `[A∣I]` 做符号 RREF，秩不足返回 null | 3 阶 |
| rank | 符号 RREF 的主元数 | 6×6 |
| transpose | 转置 | 6×6 |
| RREF | 与数值版同结构，主元「是否为 1」的判断用化简后的结构比较 | 4×4 |
| trace | 主对角求和 + 化简 | 6×6 |

**为什么限制在 3–4 阶**：符号消元的中间表达式规模随阶数指数增长，3 阶行列式展开已是 6 项多项式，4 阶 RREF 在含分母的情况下表达式体积会爆炸，浏览器会明显卡顿。这是有意的产品取舍，不是算法缺陷。

### 5.9 向量运算

| 运算 | 公式 / 实现 | 数值类型 |
|---|---|---|
| 点积 | `Σ vᵢwᵢ` | 有理数（精确） |
| 叉积 | `(v₂w₃−v₃w₂, v₃w₁−v₁w₃, v₁w₂−v₂w₁)`，仅 3 维 | 有理数 |
| 模 | `√(Σ vᵢ²)` | 浮点 |
| 单位化 | `v / ‖v‖`，零向量抛错 | 浮点 |
| 夹角 | `arccos(clamp(v·w / (‖v‖‖w‖), −1, 1))`，同时输出 rad 与 ° | 浮点 |
| 线性组合 | `αv + βw`，系数走 `safeParse` 支持分数 | 有理数 |

夹角里对点积比值做了 `clamp(−1, 1)`——浮点误差会让 `cos θ` 略微超出 `[−1,1]`，不做裁剪会得到 `NaN`。

## 6. 渲染与显示规则

| 组件 | 行为 |
|---|---|
| 矩阵渲染 `pg` | 外层用左右两条 `border-l-2/border-r-2` 竖线模拟矩阵括号；`augmentedCol` 为真时在最后一列前加竖线；尺寸 sm/md/lg 三档 |
| 单元格编辑 `A0` | 点击进入编辑，失焦/回车提交；提交时 `safeParse`，**非法则保留旧值**（不报错打断） |
| 标量结果 `hx` | 左标签右值，支持单位后缀（如 `rad`、`°`） |
| 步骤面板 `KO` | 折叠面板，逐条渲染行变换描述 + 变换后的矩阵快照 |
| 小数格式 `toDecimalString(6)` | `toFixed(6)` 后去掉末尾 0 与孤立小数点；角度用 4 位，模长用 6 位并去尾零 |
| 分数/小数开关 | 页面级状态，写入 `localStorage`，向下传给所有结果组件 |

矩阵快照在步骤里是**每步都存一份矩阵副本**（`Mf` = 深拷贝），因此步骤面板可以独立回放，不受后续计算影响。代价是内存随步骤数线性增长，10 阶矩阵的 RREF 会存几十份副本——可接受。

## 7. OCR 子系统

### 7.1 数据流

```
<input type=file accept="image/*" capture=environment>
   ↓ FileReader → dataURL
图片编辑对话框（默认整张图；canvas 旋转/翻转/裁剪 → toBlob("image/jpeg", 0.92)）
   ↓ File → FileReader → base64 dataURL
   ↓ toVisionDataUrl()：长边 > 2048 先用高质量缩放压到 2048（否则服务端粗暴降采样，细线全糊）
① 探测请求 POST {baseUrl}/chat/completions   ← buildDimensionProbePrompt()，只问「有几个、各几行几列」
   ↓ parseDimensionProbe() → [{rows:5,cols:5}]（失败则 null，不影响主流程）
② 主请求   POST {baseUrl}/chat/completions   ← buildOcrPrompt(mode, hints)，带尺寸约束
   ↓ 两次请求都带 image_url.detail = "high"（不传会被部分服务端按 512px 低清处理）
   ↓ 取 choices[0].message.content
ocr-parse.parseOcrResponse(raw)
   ├─ 剥 ```json 围栏 → 抠出第一段配对完整的 JSON
   ├─ 数组 / {"matrices":[…]} / 旧版单对象 都接受
   └─ 逐项 normalized：rows/cols 以 data 为准、短行补空、null→""、
      非方阵行列式降级为矩阵、augmented_col 1 起转 0 起
   ↓ items: OcrItem[]
   0 个 → 报「没有识别到矩阵或行列式」
   1 个 → 直接回填
   多个 → 弹 OCRResultPicker，用户挑一个
   ↓ 逐格 safeParse，失败计入 failedCells 并置 0
回填矩阵 / 提示「有 N 个单元格识别失败」
```

### 7.2 请求格式

```http
POST {baseUrl}/chat/completions
Authorization: Bearer {apiKey}
Content-Type: application/json

{
  "model": "{model}",
  "messages": [{
    "role": "user",
    "content": [
      { "type": "text", "text": "<该模式的提示词>" },
      { "type": "image_url", "image_url": { "url": "data:image/jpeg;base64,..." } }
    ]
  }],
  "temperature": 0
}
```

- `baseUrl` 结尾的 `/` 会被去掉再拼 `/chat/completions`；
- **没有** `max_tokens`、`response_format`；超时由 `AbortController` 控制（45 秒，见 8.2 / 《源码解析》），超时后抛「识别超时（45 秒无响应）」；
- `temperature: 0` 是为了让识别结果稳定；
- `image_url.detail` 传 `"high"`（v1.7 起）。不传时 OpenAI 按图片尺寸自动判断，部分兼容服务直接按 512px 低清处理，5 阶行列式的细线会糊成一团。少数不认这个字段的兼容层会返回 400，代码会检测报文里的 `detail` 关键字并自动去掉该字段重试一次；
- **一次识别 = 两次请求**（v1.7 起）：先探测尺寸（20 秒超时，失败忽略），再带尺寸约束做正式识别。成本约 1.2 倍，换来 5 阶以上不再少读行列。

### 7.3 提示词：统一返回数组（v1.6 起）

所有模式共用一套骨架（`src/lib/ocr-prompt.ts` 的 `COMMON_RULES`），只替换「模式段」：

| 模式 | 触发位置 | 模式段要点 |
|---|---|---|
| `matrix` | 单矩阵、双矩阵 A/B | 以数值为主；行列式外框是竖线、矩阵是圆括号/方括号，别混淆 |
| `system` | 线性方程组 | 优先找带竖线的 (A\|b)，`augmented: true` + `augmented_col`（**1 起算**，竖线左侧列数），`data` 含两侧全部列 |
| `symbolic` | 符号运算 | 全部按表达式字符串返回：`2a`→`"2*a"`、`x²`→`"x^2"`、`a/b`→`"a/b"`、π→`"pi"`、`x₁`→`"x1"` |

返回对象字段：`kind`（matrix/determinant）、`label`、`rows`、`cols`、`data`、`format`、`warnings`、`augmented`、`augmented_col`。

三条写进提示词的硬约束，每条都对应一次真实事故：

| 约束 | 为什么 |
|---|---|
| **始终返回 JSON 数组**，只有一个也包成 `[{...}]` | 旧版要求单对象，图里有多道题时模型只答第一个 |
| **尺寸必须来自图片**，示例明确写「不是尺寸模板」 | 旧版示例是 2×2/3×3，模型看到四阶行列式会按示例裁成左上角 2×2（v1.5 的真实 bug） |
| 行列式必须方阵，且与矩阵区分 | 竖线被当成「两列」时的典型误识别 |

### 7.4 校验与降级

解析层刻意**宽松**：形状错了就救，不轻易整条失败。

| 情况 | 处理 |
|---|---|
| 内容为空 / 完全不是 JSON | 抛错，错误信息带原文前 120 字（方便反馈给服务商） |
| 前后夹带解释文字、```json 围栏 | 剥掉围栏；失败则抠第一段括号配对完整的片段重试 |
| `{"matrices":[…]}` 包装 | 接受（提示词虽禁止，但模型常自作主张） |
| 旧版单对象 `{rows, cols, data}` | 接受，包装成 1 项 |
| 声明 `rows/cols` 与 `data` 不符 | 以 `data` 为准，记 warning「模型声明 X 行，实际 Y 行」 |
| 行内列数不齐 | 按最长行补空串，记 warning |
| 单元格 `null` | 转 `""`，记 warning，回填时按 0 处理并计入 failedCells |
| 行列式非方阵 | 降级为 `matrix`，记 warning |
| `augmented_col` 越界 | 忽略，记 warning |
| 元素总数 > 400（20×20） | 丢弃该项并记 warning，防病态数组卡死页面 |

最后两级的理念是**「宁可让用户核对几个格子，也不要整张图白识别」**——但尺寸问题例外：以 `data` 为准而不是硬塞成声明的尺寸，因为缩尺寸会静默丢数据。

### 7.5 事故复盘：四阶行列式只认出 2×2（v1.6 修复）

| 项 | 内容 |
|---|---|
| 现象 | 上传一张含 4×4 行列式的图，返回 2×2，且没有任何报错 |
| 直接原因 | 提示词里的 JSON 示例是 2×2/3×3，模型把它当成了输出模板 |
| 根因 1（提示词） | 旧提示词通篇没提「行列式」「竖线」「多个矩阵」，只要求「识别这张图片中的矩阵」，返回单个对象 |
| 根因 2（解析器） | 只接受 `{rows, cols, data}` 单对象；模型真要按数组返回反而会报「识别结果格式不正确」——即提示词和解析器互相锁死在「一个矩阵」上 |
| 修复 | 提示词改成数组契约 + 四阶示例 + 「示例不是尺寸模板」；解析器改为宽容数组解析并在尺寸不符时以 `data` 为准；UI 加多结果选择框 |
| 回归 | `tests/build-and-test.mjs` 的 OCR-01 直接断言「四阶行列式不被截成 2×2」；OCR-05 断言提示词里必须还有「不是尺寸模板」这句话 |
| 教训 | **示例的尺寸会被模型当成规范**。给视觉模型的 JSON 示例，要么尺寸与常见题一致，要么显式声明「示例仅示范格式」 |

**第二轮（v1.7）：改成数组契约后，5 阶仍然只出低阶行列式。** 说明格式层之外还有三个更靠前的原因，逐条查下来：

| # | 原因 | 证据 | 修复 |
|---|---|---|---|
| 1 | **图片编辑器默认裁掉四周 5%**（5%/90% 的框） | 代码里 `crop = {x:5,y:5,w:90,h:90}`；5 阶行列式占满画面时最外一行/一列正好被切 | 默认改成 `{0,0,100,100}`（整张图），并在界面上写明 |
| 2 | **裁剪框坐标系与导出坐标系不一致** | 预览用 `object-contain` 的 4:3 容器，框按容器百分比画；导出按图片百分比切 → 看到的和切下来的不是一块 | 预览框改成按原图比例计算（`box = 图片 aspect`），并让拖拽按图片框的 rect 换算 |
| 3 | **图片送进去时没有「高精度」标记，也没做尺寸控制** | 请求体 `image_url` 只有 `url`；原图 4000px 会被服务端降采样 | 加 `detail: "high"`；长边 > 2048 先本地高质量缩放 |
| 4 | **模型数不清行列** | 直接生成 data 时按 token 走，写错也没机会回头数 | 先发一次极简「尺寸探测」，把 `[{rows:5,cols:5}]` 作为硬约束塞进主提示词 |

验证方式：`node tests/ocr-e2e.mjs`（假模型 + headless Chrome 真点界面），11 项断言覆盖「默认整图 / detail=high / 尺寸提示注入 / 5×5 回填」。这套测试不需要真实 Key。

## 8. 存储与状态

全部状态在 `localStorage`，无后端、无账号体系（`window.userId` 为 `guest`）。

存储键带宿主前缀，由 `__miaoda_${appId || "__global__"}__:` + 业务键拼接：

| 业务键 | 内容 | 写入时机 |
|---|---|---|
| `__app_linalg_ocr_config` | `{"baseUrl","apiKey","model"}` | 保存/清除 OCR 配置 |
| `__app_linalg_fraction_mode` | `"true"` / `"false"` | 顶栏「小数模式 / 分数模式」开关 |

`appId` 来自页面注入的 `window.appId`：

- HTML 版注入 `linear-algebra-calculator` → 键形如 `__miaoda_linear-algebra-calculator__:__app_linalg_ocr_config`；
- APK 版注入空串 → 走 `__global__` 分支。

**排查/清理方法**（浏览器控制台）：

```js
// 列出本应用写入的所有键
Object.keys(localStorage).filter(k => k.includes('linalg'));

// 只清 OCR 配置（会同时清掉所有前缀下的同名键）
Object.keys(localStorage)
  .filter(k => k.endsWith('__app_linalg_ocr_config'))
  .forEach(k => localStorage.removeItem(k));
```

此外宿主 SDK 会写一个 `x_sdk_device_id`（设备标识，随机生成并持久化），与业务无关。

## 9. 网络行为与离线能力

| 请求 | 触发条件 | 失败影响 |
|---|---|---|
| `@import https://miaoda.feishu.cn/fonts/css2?...`（字体） | HTML 版加载时 | 回退系统字体（`PingFang SC` / 微软雅黑等），布局不受影响 |
| `GET /app/<appId>/routes.json`（宿主路由表） | HTML 版启动 | 捕获异常后回退为 `[{path:"/"}]`，单页应用照常工作 |
| 宿主埋点/指标上报 | HTML 版运行期 | 静默失败，不影响功能 |
| `POST {用户配置的 baseUrl}/chat/completions` | 用户点识别 | 报错提示，已有矩阵不被清空 |

**离线结论**：矩阵、方程组、向量、符号四类计算完全离线；OCR 必须联网；HTML 版的字体与宿主请求在离线时会失败但不阻塞使用。产物**没有 Service Worker**，因此不是 PWA，离线能力来自「资源已内联/已打包」而不是缓存策略。

## 10. 复杂度与规模上限

| 操作 | 上限 | 复杂度 | 备注 |
|---|---|---|---|
| 数值矩阵输入 | 10×10 | — | 100 个格子，DOM 压力可接受 |
| RREF / rank / inv | 10×10 | O(m²n) | 精确分数，最坏情况分子分母膨胀 |
| det | 10×10 | O(n³) | 主元启发式降低膨胀 |
| power | 10×10，指数为 int | O(log n · k³) | 快速幂 |
| eigen | 5×5（UI 限制） | O(100 · n³) | QR 迭代上限 100 次；> 5 阶提示「特征值计算最多支持 5 阶矩阵」 |
| 方程组 | 10 行 × (1–10 未知数 + 1) | O(m²n) | 与 RREF 同；`maxCols=11` |
| 符号 RREF | 4×4 | 表达式规模主导 | 无严格时间上界 |
| 符号 det / inv | 3 阶 | 显式公式 | 常数时间 |
| 向量 | 2–5 维 | O(n) | |
| OCR | 图片大小不限 | 网络与模型主导 | 图片仅在客户端压缩，未做尺寸上限保护 |

## 11. 已知限制与风险

按影响程度排序。编号可在 issue / 测试用例中引用。

| 编号 | 问题 | 影响 | 建议 |
|---|---|---|---|
| L1 | 有理数用 double 存储分子分母 | 大数/高阶分数矩阵越界后**静默失去精确性** | 改 `BigInt`；或在中途检测 `> 2^53` 时提示「结果已超出精确范围」 |
| L2 | n≥3 特征值仅支持实特征值 | 复特征值矩阵给出错误/不收敛的对角元，且**无收敛标志** | QR 后检查次对角元是否收敛，未收敛则提示；或实现 2×2 块提取（real Schur） |
| L3 | 重特征值的特征向量可能重复 | 反幂法对重根收敛到同一方向 | 用零空间基（RREF of A−λI）替代逆迭代，重根时返回多个基向量 |
| L4 | OCR 请求无超时/中断 | 接口挂起时界面停在 loading | **已修复（v1.2 源码）**：`AbortController` + 45s 超时，超时抛「识别超时（45 秒无响应）」，`finally` 清理定时器 |
| L5 | API Key 明文存 `localStorage` | 本机被他人使用时泄露 | 至少做混淆/会话级存储，并在文档中明确风险（详见《可行性-视觉模型配置存储》） |
| L6 | 单文件版依赖宿主运行时 | 体积 1.2 MB、含埋点代码、离线加载字体失败 | 如需纯净版，用 APK 那套分块构建自行打包静态站 |
| ~~L7~~ | ~~非法输入静默保留旧值~~ | **经源码复核：不成立**。`MatrixCell` 解析失败时输入框变红、保持编辑态、不提交，符合 PRD | 已从缺陷表移除 |
| L8 | 没有「复制结果」按钮 | 该函数来自平台库 `@lark-apaas/client-toolkit-lite`，业务代码未接；用户只能框选复制 | 在结果卡加「复制」按钮并调用库函数，或自行实现 |
| L9 | 符号 RREF 上限 4×4 无提示入口 | 用户看到按钮变灰却不知原因 | 在卡片上标注「≤4×4」 |
| L10 | 方程组未知数上限 10（列 11）、矩阵上限 10×10 未在 UI 标明 | 加到上限时按钮禁用，原因不明 | 加 tooltip |
| L11 | 无测试框架 | 只有 `tests/build-and-test.mjs` 自建断言（18 项，覆盖方程组） | 引入 Vitest，覆盖 `matrix-ops` / `symbolic` / `fraction` 全量 |
| L12 | ~~产物是压缩 bundle，无法改功能~~ | **源码已到位**（`source/`），可本地构建 | 见《开发者指南》与《源码解析》第 9 节 |
| L13 | 方程组「无解」时 `rankAb` 恒等于 `rankA` | 界面打印「1 与 1，秩不相等故无解」这种错误文案，结论对但数字错 | **已修复（v1.2 源码）**：`rankAb` 改为统计行最简形的非零行数 |

> **状态说明**：L4、L13 已在 v1.2 源码中修复；L7 经复核不成立，已移除；其余为待办项。
> v1.1 曾在压缩产物上做过等价的字节级补丁，现已由源码修复取代，补丁仅作历史归档（第 14 节）。

## 12. 安全与隐私

- **计算不出网**：所有矩阵运算在本地完成，没有任何上传结果的路径；
- **唯一外发**：OCR 时上传用户主动选择的图片（base64）到用户自己配置的服务商；
- **密钥**：仅存本机 `localStorage`，不走任何中转；但为明文，公用设备需谨慎；
- **APK 权限**：对外权限以 `INTERNET` 为主，未见存储/相机权限——拍照是通过系统文件选择器的 `capture` 属性完成的，因此不需要 `CAMERA`；
- **无账号体系**：`userId` 固定为 `guest`，不存在登录态泄露面。

### 14.3 三个必须知道的构建坑

1. **原生可选依赖缺失**（`@rolldown/binding-win32-x64-msvc`、`lightningcss-win32-x64-msvc`、`@tailwindcss/oxide-win32-x64-msvc`）。`package-lock.json` 在他平台生成，npm 不会自动补 Windows 二进制，报 `Cannot find module …win32-x64-msvc`。必须**一条命令装齐**（`--no-save` 会被下一次 install 清理）：
   ```bash
   npm install --no-save @rolldown/binding-win32-x64-msvc@1.2.7 \
     lightningcss-win32-x64-msvc@1.32.0 @tailwindcss/oxide-win32-x64-msvc@4.3.3
   ```
2. **`fs.cpSync` 在本机会静默崩溃**（退出码 127，无输出，`try/catch` 抓不到）。已把 `make-standalone.mjs` 改成手写递归复制。
3. **路径含中文 + OneDrive**：Vite 本身没问题，但建议仓库放纯 ASCII 路径（如 `D:////projects////linalg`），可减少脚本层的意外。
