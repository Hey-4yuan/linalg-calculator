线性代数计算器

一个纯前端、可离线使用的线性代数计算器，支持精确分数运算的矩阵计算、线性方程组求解、向量运算、符号矩阵运算，以及基于视觉大模型的图片识别录入。

计算全部在浏览器本地完成，不依赖后端；唯一的外发请求是用户在设置中自行配置的 OCR 大模型接口。

源码已归档到 source/，产物由源码构建（v1.2），可以本地改、本地出包。

一、交付物

产物 文件 形态 说明
Web 单文件版 线性代数计算器.html（1.24 MB） 单 HTML 内联全部 JS/CSS，双击即用 v1.2 源码构建
Android 应用 线性代数计算器.apk（4.2 MB） Capacitor 6 壳 + 本地 Web 资源，包名 com.doubao.linalg v1.0 旧构建；源码工程的网页资源已更新，重打包即得 v1.2
图像识别手册 线性代数计算器图像识别功能使用手册.pdf 5 页图文，手机端 OCR 配置流程 首次配置 API Key 的新手

两种前端产物来自同一份源码：Web 版是「单文件内联」，APK 版是「分块资源 + Capacitor 壳」。功能一致，存储键同格式。

v1.2 相比 v1.0 修了两个问题：方程组「无解」时增广矩阵秩显示错误（L13）、OCR 请求无超时（L4）。改动在源码里，不是对压缩产物的补丁。 v1.5 补了 iOS 交付细节（应用内「添加到主屏」引导、存储风险提示）和结果卡「复制」按钮；v1.6 修了 OCR 只能认出 2 阶（提示词与解析器都改成数组契约，支持行列式与一图多题）。

二、功能总览

模块 能力 规模上限 精度策略
单矩阵运算 行列式 det、逆矩阵、秩 rank、转置 Aᵀ、行最简形 RREF、特征值/特征向量、迹 tr、幂 Aⁿ 10×10；特征值 ≤ 5 阶 det/逆/RREF/幂 为精确分数；特征值为数值近似
双矩阵运算 A + B、A − B、A × B 10×10 精确分数
符号运算 含字母与 π 的矩阵：det、inv、rank、transpose、RREF、trace 6×6（det/inv ≤ 3 阶，RREF ≤ 4×4） 符号表达式精确化简
线性方程组 增广矩阵输入 → 唯一解 / 无穷多解（自由变量 + 基础解系）/ 无解，附高斯消元步骤 10 行 × (1–10 未知数 + 1) 精确分数
向量运算 点积、叉积（仅 3 维）、模、单位化、夹角（rad + °）、线性组合 2–5 维 点积/组合为精确分数，模与夹角为浮点
图片识别 拍照/选图 → 裁剪旋转翻转 → 视觉模型识别；三种模式（数值矩阵 / 符号矩阵 / 增广矩阵）；支持行列式（|…|）与一图多题（识别后选择载入） 由模型与提示词约束 识别失败单元格置 0 并提示核对；尺寸以图片实际行列数为准

顶栏右侧的开关（标签在「小数模式」/「分数模式」之间切换）决定所有结果的呈现方式：小数模式显示 6 位小数（自动去尾零），分数模式显示 p/q。开关状态随浏览器本地保存。

每张结果卡右上角有「复制」：复制成制表符分列的纯文本，粘到 Excel / WPS 表格会自动分格。

iPhone / iPad：部署到 HTTPS 后建议先「分享 → 添加到主屏幕」再用。Safari 标签页里的本地数据（含 OCR 的 API Key）在 7 个「使用日」无交互后会被系统清理，主屏幕 Web App 使用独立存储，不受这条规则影响。应用内会主动弹提示。

三、快速开始

Web 版：双击 线性代数计算器.html → 直接可用。首次打开无需联网（字体走系统回退），OCR 功能需先配置。

APK 版：安装 线性代数计算器.apk → 打开即用（仅申请网络权限，用于 OCR）。

配 OCR（两版通用）：在任意矩阵卡片标题右侧点「配置 OCR」→ 填 Base URL、API Key、视觉模型名 → 保存。要求接口兼容 OpenAI Chat Completions 协议且支持图像输入。以 DeepSeek 中转为例：

Base URL: https://api.deepseek.com
视觉模型名: deepseek-flash
API Key:  自行申请（见附图手册）

保存后按钮变成「图片识别」，旁边多一个齿轮「OCR 设置」。

API Key 以明文保存在浏览器 localStorage，不会上传到任何第三方；换设备或清缓存后需重新填写。不要使用他人共享的 Key，也不要把自己的 Key 发给别人。 存储边界与加固方案见 docs/可行性-视觉模型配置存储.md。

六、必须知道的三条限制

  1. 矩阵数值全部走 JS 的 number（Fraction 内部是 num/den 两个 double）。元素绝对值超过 2^53 或分数分子分母累乘过大时会出现精度漂移，此时结果不再严格精确。
  2. n ≥ 3 的特征值用 QR 迭代近似（100 次 / 容差 1e-10），只保证实特征值收敛；复特征值仅在 2×2 时专门处理；阶数上限 5。
  3. 产物不要手改。压缩后的 bundle 可读性差，改了下次构建就丢；改 source/ 再 npm run build:all。

4. 矩阵运算

4.1 单矩阵运算

输入一个矩阵后，点右侧任一运算按钮，结果立即出现在右侧卡片。

按钮 数学含义 前置条件 结果形式
行列式 det det A 方阵 精确值（分数）
逆矩阵 A⁻¹ 方阵且可逆 矩阵；不可逆时提示「该矩阵不可逆（奇异矩阵），行列式为 0」
秩 rank rank A 无 整数
转置 Aᵀ Aᵀ 无 矩阵
行最简形 RREF 行最简形 无 矩阵 + 主元列说明

幂 Aⁿ 怎么用

点「幂 Aⁿ」后弹出指数输入框，输入整数（如 5、-2、0）再点计算：

  • n > 0：快速幂，n = 0 得单位矩阵；
  • n < 0：先求逆再取正幂，因此矩阵必须可逆；
  • 非整数（1.5）报「请输入有效的整数指数」。

计算步骤

行列式、逆矩阵、RREF、方程组都会附「计算步骤」面板，可逐条展开查看每一步的行变换，记号约定：

记号 含义
R1 ↔ R2 交换第 1、2 行
R2 ← R2 × 1/3 第 2 行乘以 1/3
R3 ← R3 − 2R1 第 3 行减去第 1 行的 2 倍

逆矩阵的步骤是以 [A | I] 为起点做的，所以面板里会看到一个增广矩阵。

示例

A = 1  2  3
    4  5  6
    7  8 10
  • det(A) = −3
  • rank(A) = 3
  • tr(A) = 16
  • 逆矩阵可用（det ≠ 0）

4.2 双矩阵运算

分别填好「矩阵 A」和「矩阵 B」，卡片下方会实时显示维度是否匹配：

运算 按钮 条件 提示文案（不匹配时）

5. 线性方程组

把方程组写成增广矩阵 [A | b] 输入。默认列标题为 x1 x2 … xn | b，最后一列是常数列。

 2x₁ +  x₂ −  x₃ =  8
−3x₁ −  x₂ + 2x₃ = −11      →    [ 2  1 -1 |  8 ]
−2x₁ +  x₂ + 2x₃ = −3            [-3 -1  2 | -11 ]
                                  [-2  1  2 | -3 ]

5.1 尺寸控制

控件 范围 说明
方程数 1–10 即行数
未知数 1–10 即列数 − 1（列数 2–11）；改未知数时增减的总是增广列之前的部分，b 列始终留在最后

5.2 求解与结果

点「求解」后，右侧「求解结果」卡片给出三种结论之一：

结论 界面表现 含义
唯一解 绿色标题 + 各变量取值 rank A = rank [A∣b] = n
无穷多解 黄色标题 + 自由变量列表 + 特解 + 基础解系 η 秩相等但小于未知数个数 n
无解 红色标题 + 「方程组存在矛盾方程，没有解。」 + 秩对比说明 rank A ≠ rank [A∣b]，消元后出现 0 = 非零常数 的矛盾行

关于秩的显示（v1.2 已修复）：早先版本这句话里的两个秩会打印成同一个值（例如 1 和 1）。当前产物由源码重新构建，无解时会正确显示 系数矩阵秩 = 1，增广矩阵秩 = 2，秩不相等故无解。若你手上的副本仍是旧版，重新构建或取最新产物即可。

无穷多解的通解形式为：

x = 特解 + c₁η₁ + c₂η₂ + ⋯

界面会分别给出「通解形式」「自由变量」「基础解系 η」三块内容，可直接抄进作业。

「高斯消元过程」面板展示每一步行变换，增广列前有竖线分隔，方便对照。

5.3 快速示例按钮

按钮 载入的方程 结果
唯一解 上文 3 元方程组 x₁ = 2，x₂ = 3，x₃ = −1

判断「无解 / 无穷多解」的依据是秩，不是行列式——非方阵或不齐次时，行列式那套判据不适用。

7. 图片识别（OCR）

作用：把纸上/截图里的矩阵拍成图片自动填进输入框，省去手输十几格。

7.1 一次性配置

  1. 在任意矩阵卡片标题右侧点「配置 OCR」（单矩阵、双矩阵 A/B、符号矩阵、方程组各有一个）；
  2. 填写三项： - Base URL：接口根地址，需兼容 OpenAI Chat Completions（如 https://api.openai.com/v1、https://api.deepseek.com）； - API Key：你自己的密钥； - 视觉模型名：必须支持图像输入（gpt-4o-mini、gpt-4o、claude-3-5-sonnet、deepseek-flash 等）；
  3. 「保存配置」，按钮由「配置 OCR」变为「图片识别」；旁边会多出一个齿轮按钮「OCR 设置」，之后想改配置点它。

配置存在浏览器本地，换浏览器/清缓存/换设备都要重填。密钥明文存储，勿在公用电脑上配置。

7.2 识别流程

点识别按钮 → 选择/拍摄图片 → 图片编辑（可选）→ 确认并识别 → 自动填入矩阵

图片编辑对话框提供：

操作 说明
拖动裁剪框 / 拖四角控制点 只保留矩阵区域，能显著提升识别率
左转 / 右转 每次 90°，把横拍的照片摆正
水平翻转 / 垂直翻转 处理镜像图
重置 复原旋转、翻转与裁剪框
确认并识别 导出 JPEG 后上传识别

建议：把矩阵裁到只剩数字与括号，去掉题号、手写批注、阴影；光线均匀、字迹与底色对比明显时准确率最高。

7.3 三种识别模式

不同模块调用不同的识别模式，提示词不同：

模块 模式 期望图片内容
矩阵 A / 矩阵 B / 单矩阵 数值矩阵 纯数字矩阵或行列式（含分数、负数）
符号运算 符号矩阵 含字母、π、运算符的矩阵
线性方程组 增广矩阵 增广矩阵，带 ∣ 或虚线分隔常数列

行列式也能识别：|…| 或 det(…) 会被识别成方阵并填进网格，之后点「行列式 det」即可求值。

7.4 一张图里有多道题

识别完成后先判断结果数量：

识别到几个 界面行为
0 个 提示「没有识别到矩阵或行列式，请调整裁剪范围或换一张更清晰的照片」
1 个 直接填入矩阵，并提示「识别成功：A 矩阵 3×3」
多个 弹出选择框，列出每个结果的序号、名称（A、det(A)、(1)…）、类型、尺寸和首行内容，点一个载入

为什么要选：计算器一个面板只放得下一个矩阵，一次全塞进去没有意义。拍整页作业时，先挑你要算的那一道。

尺寸以图片实际行列数为准：四阶行列式就是 4×4，不会被截成 2×2（v1.6 修的问题）。

7.5 识别结果的处理

  • 识别成功：直接覆盖当前矩阵，并提示「识别成功：A 矩阵 3×3」；
  • 部分单元格无法解析（模型返回了 1/0、乱码、null 等）：这些格子被置为 0，并弹出「有 N 个单元格识别失败，已置为 0，请核对」——务必人工核对这几个格子；
  • 模型给的尺寸与内容不符：以实际内容为准（不会按声明的尺寸硬塞），并提示「模型声明 4 行，实际 2 行，已按实际处理」；
  • 行列式不是方阵（比如竖线被误读）：降级成普通矩阵并提示；
  • 网络错误、鉴权失败、额度耗尽等：显示服务端返回的状态码与内容，例如 API 请求失败 (401): ...、应用额度已耗尽，请联系应用开发者。

识别只是「录入加速器」，不改变计算逻辑。识别后的一切计算仍是本地精确运算。

10. 典型使用流程

核对作业（最常用）

  1. 矩阵运算 → 单矩阵运算 → 手输矩阵；
  2. 点「行列式 det」看值与步骤，与手算比对；
  3. 点「计算步骤」逐步核查行变换，找出自己算错的那一步；
  4. 顶栏切换到「分数模式」，确认结果是 1/3 还是 0.333333。

解方程组

  1. 线性方程组 → 把每行系数与常数填进增广矩阵（列数 = 未知数 + 1）；
  2. 「求解」→ 看结论类型；
  3. 如果是无穷多解，抄「特解 + 基础解系」；
  4. 展开「高斯消元过程」写解题步骤。

手机快速录入

  1. 拍照 → 识别 → 编辑器里裁掉题号与手写内容；
  2. 识别后核对被置 0 的格子；
  3. 继续在线计算。

11. FAQ

Q：断网还能用吗？ A：能。所有计算在前端完成；只有 OCR 需要联网（调你自己配置的模型接口）。网页版首次加载时字体走 CDN，失败会自动回退系统字体，不影响功能。

Q：数据会上传吗？ A：计算结果不会。只有 OCR 时，你选中的那张图片会以 base64 发给你配置的模型服务商；API Key 只存在本机 localStorage。

Q：为什么 3 阶以上的特征值有小数尾巴？ A：n≥3 用 QR 迭代求特征值、反幂法求特征向量，本质是数值方法，容差 1e-10、最多 100 次迭代。要精确值请手算或看 2×2 的解析结果。

Q：特征值为什么会缺？ A：3 阶及以上目前只输出实特征值；如果矩阵有复特征值，只有 2×2 会被正确识别为复数对。

Q：为什么输入 2a 没被当成 2×a？ A：符号解析器把连续字母当作一个变量名。乘号请显式写 2*a。

Q：换手机 / 清缓存后 OCR 配置没了？ A：配置存在浏览器本地，不会同步。重新填一次即可。

4. 数值核心：有理数类

4.1 表示

class Fraction {
  num;  // 分子，JS number

4.3 精度边界

num、den 是 IEEE-754 double，只有 |num|、den ≤ 2⁵³ 时运算才严格精确：

  • 10×10 的整数矩阵做完 RREF 后，中间量的分子分母通常仍在 10⁶ 量级，安全；
  • 但含大整数（如元素是 10 位以上）、或 10 阶分数矩阵做行列式展开时，分子分母会快速膨胀，可能越过 2⁵³ 而悄悄失去精确性；
  • 这不是可选优化，而是当前实现的硬边界。若要彻底解决，需把 num/den 换成 BigInt。

5. 算法实现

矩阵统一用行优先二维数组表示。分两种元素类型：有理数（数值模式）与符号表达式 AST（符号模式），两者算法结构对称、实现分离。

5.1 行最简形 RREF（rref）

Gauss-Jordan 消元，主元采用整数友好策略（与行列式同一套评分函数）：

pivotFriendliness(f) = 0                       若 f 是整数
                     = f.den + |f.num| × 0.1   否则
score(f) = pivotFriendliness(f) × 1000 − |f|

m = 0
for col in 0 .. 系数列数-1:
    在 i ≥ m 的行中，选 score(A[i][col]) 最小的非零元作主元
    if 无主元: continue
    if pivotRow ≠ m: 交换 R_m, R_pivotRow        → step{type:"swap"}
    if A[m][col] ≠ 1:
        整行乘以 1/A[m][col]                     → step{type:"scale"}
    for i in 0..rows-1, i ≠ m:
        if A[i][col] ≠ 0:
            R_i ← R_i − A[i][col]·R_m            → step{type:"add"}
    pivotCols.push(col); m++
return { rref, rank: pivotCols.length, pivotCols, steps }

要点：

  • 主元不是"第一个非零"，而是"算起来最省事的"：优先整数主元，其次分母小的；同分时取绝对值大的（数值更稳）。这是为了让消元过程尽量不产生复杂分数——既好看也好核对；
  • 归一化只在主元不为 1 时执行（少一步无意义的 × 1）；
  • 消去所有行（含上方），一次跑完即得行最简形；
  • 步骤只有三种：swap / scale / add，渲染为 R₂ ← R₂ − 3R₁（行号用 Unicode 下标）；
  • augmentedCols > 0 时（方程组、求逆），最后一列/右侧块不参与主元选择，但仍参与行变换——保证「常数列不能当主元」；
  • 精确算术下这种主元选择不影响正确性，只影响步骤最短与中间分数规模。

复杂度 O(min(m,n)·m·n)。源码位置：src/lib/matrix-ops.ts 的 rref()。

5.2 行列式（determinant）

同样是「消元到上三角再乘对角」，但带主元启发式，目的是压制分数膨胀：

for m in 0 .. n-1:
    # 选主元：优先整数（分母为 1），其次分母小、分子小
    pivotScore(S) = 0                        if S 是整数
                  = S.den + |S.num| * 0.1    otherwise
    v = argmin over i ≥ m of ( pivotScore(S) * 1000 − |S| )
    if 该列全零: return det = 0
    if v ≠ m: 交换 → sign = −sign，记录 step
    for i in m+1 .. n-1:
        # 只对下方消元，不做归一化
        倍数 = −A[i][m] / A[m][m]
        R_i ← R_i + 倍数·R_m                 → 记录 step
det = sign · Π A[i][i]

关键取舍：

  • 不归一化主元行——避免了除法带来的分母膨胀，最后的 det 由「符号 × 对角乘积」直接得到；
  • 主元评分里 ×1000 让「是否整数」成为最高优先级，− |S| 在同类中偏向绝对值大的（数值更稳）；
  • 与 RREF 使用同一套 pivotFriendliness 评分（见 5.1），区别只在于 det 不做归一化、只消下方；
  • 源码里 detScale 变量恒为 Fraction.ONE（从未被修改），属于死代码，可删。

5.3 逆矩阵（inverse）

构造 [A | I]（n × 2n）
对前 n 列做 RREF（augmentedOffset = n）
if rank < n: return null   // 奇异，视图层提示「该矩阵不可逆」
return RREF 的右侧 n 列

步骤面板展示的正是这个 [A|I] 的化简过程。

5.4 秩 / 迹 / 转置

运算 实现
rank 直接取 RREF().rank（主元个数）
trace Σ A[i][i]，循环 min(rows, cols)（非方阵取较短的主对角）
transpose 行列互换，返回新矩阵，不改原值

5.5 矩阵幂（matrixPower）

if 非方阵: 抛「矩阵幂要求方阵」
if n 不是整数: 抛「指数必须为整数」
if n < 0: A⁻¹ 存在则递归求 (A⁻¹)^(−n)，否则抛「负指数要求矩阵可逆」
if n == 0: 返回 I
二进制快速幂：结果 = I; 底 = A
while n > 0: if n 奇数: 结果 = 结果 × 底; 底 = 底 × 底; n >>= 1

全程有理数精确运算，10 阶矩阵 30 次幂仍在毫秒级。

5.6 特征值与特征向量（eigenvalues）

先统一转成浮点（这是全应用唯一的浮点主路径），再按阶数分支：

入口限制：SingleMatrixSection 在调用前判断 size > 5 → 直接报错，因此实际最多 5 阶。

阶数 方法 说明
1 直接取 A[0][0] 特征向量取 [1]
2 解析解：λ = (tr ± √(tr² − 4det)) / 2 判别式 < 0 时返回 complexEigenvalues = [{real, imag}, {real, −imag}]，此时 eigenvalues 为空
n ≥ 3 QR 迭代 见下

QR 迭代（M$）：

  • 对当前矩阵做 QR 分解（Gram-Schmidt 正交化，遇到近似零列时补标准基向量）；
  • A ← R·Q，重复至多 100 次，判据是下三角部分所有元素绝对值 ≤ 1e-10；
  • 收敛后取对角线作为特征值，降序排列。

特征向量（fO）：对每个 λ 做反幂法/逆迭代——解 (A − λI)x = b（部分主元高斯消元 + 回代），归一化后与上一次迭代比较，最多 50 次，初值取 (1/√n, …, 1/√n)。

界面提示：「特征值与特征向量采用数值方法近似计算，结果可能存在微小误差」——用户手册中也强调 3 阶以上只有实特征值。

5.7 线性方程组（solveLinearSystem）

输入是增广矩阵 [A|b]，变量名按 x1 … xn（n = 列数 − 1）生成。

{rref, rank, pivotCols, steps} = RREF([A|b], augmentedOffset = 1)
rankA = |pivotCols|, rankAb = rank

# 1) 矛盾判定：存在「系数全零但常数非零」的行
for each row: if 前 n 列全零 且 常数列非零 → 无解

# 2) 唯一解：rankA == n
if rankA == n: x[i] = rref[i][n]

# 3) 无穷多解：rankA < n
自由变量 = 非主元列对应的变量
特解：主元变量取 rref[行][常数列]，其余为 0
基础解系：对每个自由变量 f
    η[f] = 1
    每个主元行 r：η[pivotCols[r]] = −rref[r][f]

返回值结构：

{ type: "unique"   , solution, rankA, rankAb, rref, pivotCols, variableNames, steps }
{ type: "infinite" , freeVariables, particularSolution, basisVectors, rankA, rankAb, ... }
{ type: "no-solution", rankA, rankAb, ... }

三个结论分别对应 rankA = rankAb = n、rankA = rankAb < n、rankA ≠ rankAb 三种情形，与线性代数教材判据一致。

已修复（源代码修复，v1.2）：原实现把 rref(augmented, 1) 返回的 rank 当作 rankAb，而该调用的主元只在系数列内选取，所以 rankAb 恒等于 rankA，界面会打印「系数矩阵秩 = 1，增广矩阵秩 = 1，秩不相等」。 修复后直接按定义算：rankAb = 行最简形中非零行的行数（行变换不改变行空间维数）。 无解结论本身一直是对的（由「系数全零但常数非零」的矛盾行判定），错的只是展示值。详见《源码解析》8.1。

解析

递归下降 + 词法分析：

  • 词法：数字、标识符（连续字母+数字）、运算符 + − * / ^、括号 ( )；× ÷ 视同 * /；π 视同标识符 pi；
  • 语法：expr → term (('+'|'-') term)*，term → factor (('*'|'/') factor)*，factor → base ('^' factor)?，base → num | ident | '(' expr ')' | '-' base；
  • 解析结束后若还有剩余 token，报「表达式未完全解析，多余: …」；
  • 每次构造节点都会做一次化简（合并常数、消去 0/1、合并同类项的最小子集），所以 a*1 直接得到 a。

各运算

ocr-parse.parseOcrResponse(raw)
   ├─ 剥 ```json 围栏 → 抠出第一段配对完整的 JSON
   ├─ 数组 / {"matrices":[…]} / 旧版单对象 都接受
   └─ 逐项 normalized：rows/cols 以 data 为准、短行补空、null→""、
      非方阵行列式降级为矩阵、augmented_col 1 起转 0 起
   ↓ items: OcrItem[]
   0 个 → 报「没有识别到矩阵或行列式」
   1 个 → 直接回填
   多个 → 弹 OCRResultPicker，用户挑一个
   ↓ 逐格 safeParse，失败计入 failedCells 并置 0
回填矩阵 / 提示「有 N 个单元格识别失败」

POST {baseUrl}/chat/completions
Authorization: Bearer {apiKey}
Content-Type: application/json

{
  "model": "{model}",
  "messages": [{
    "role": "user",
    "content": [
      { "type": "text", "text": "<该模式的提示词>" },

  • baseUrl 结尾的 / 会被去掉再拼 /chat/completions；
  • 没有 max_tokens、response_format；超时由 AbortController 控制（45 秒，见 8.2 / 《源码解析》），超时后抛「识别超时（45 秒无响应）」；
  • temperature: 0 是为了让识别结果稳定。

7.3 提示词：统一返回数组（v1.6 起）

所有模式共用一套骨架（src/lib/ocr-prompt.ts 的 COMMON_RULES），只替换「模式段」：

模式 触发位置 模式段要点
matrix 单矩阵、双矩阵 A/B 以数值为主；行列式外框是竖线、矩阵是圆括号/方括号，别混淆
system 线性方程组 优先找带竖线的 (A|b)，augmented: true + augmented_col（1 起算，竖线左侧列数），data 含两侧全部列
symbolic 符号运算 全部按表达式字符串返回：2a→"2*a"、x²→"x^2"、a/b→"a/b"、π→"pi"、x₁→"x1"

返回对象字段：kind（matrix/determinant）、label、rows、cols、data、format、warnings、augmented、augmented_col。

三条写进提示词的硬约束，每条都对应一次真实事故：

约束 为什么
始终返回 JSON 数组，只有一个也包成 [{...}] 旧版要求单对象，图里有多道题时模型只答第一个
尺寸必须来自图片，示例明确写「不是尺寸模板」 旧版示例是 2×2/3×3，模型看到四阶行列式会按示例裁成左上角 2×2（v1.5 的真实 bug）
行列式必须方阵，且与矩阵区分 竖线被当成「两列」时的典型误识别

7.4 校验与降级

解析层刻意宽松：形状错了就救，不轻易整条失败。

情况 处理
内容为空 / 完全不是 JSON 抛错，错误信息带原文前 120 字（方便反馈给服务商）
前后夹带解释文字、```json 围栏 剥掉围栏；失败则抠第一段括号配对完整的片段重试
{"matrices":[…]} 包装 接受（提示词虽禁止，但模型常自作主张）
旧版单对象 {rows, cols, data} 接受，包装成 1 项
声明 rows/cols 与 data 不符 以 data 为准，记 warning「模型声明 X 行，实际 Y 行」
行内列数不齐 按最长行补空串，记 warning
单元格 null 转 ""，记 warning，回填时按 0 处理并计入 failedCells
行列式非方阵 降级为 matrix，记 warning
augmented_col 越界 忽略，记 warning
元素总数 > 400（20×20） 丢弃该项并记 warning，防病态数组卡死页面

最后两级的理念是「宁可让用户核对几个格子，也不要整张图白识别」——但尺寸问题例外：以 data 为准而不是硬塞成声明的尺寸，因为缩尺寸会静默丢数据。

7.5 事故复盘：四阶行列式只认出 2×2（v1.6 修复）

项 内容
现象 上传一张含 4×4 行列式的图，返回 2×2，且没有任何报错
直接原因 提示词里的 JSON 示例是 2×2/3×3，模型把它当成了输出模板
根因 1（提示词） 旧提示词通篇没提「行列式」「竖线」「多个矩阵」，只要求「识别这张图片中的矩阵」，返回单个对象
根因 2（解析器） 只接受 {rows, cols, data} 单对象；模型真要按数组返回反而会报「识别结果格式不正确」——即提示词和解析器互相锁死在「一个矩阵」上
修复 提示词改成数组契约 + 四阶示例 + 「示例不是尺寸模板」；解析器改为宽容数组解析并在尺寸不符时以 data 为准；UI 加多结果选择框
回归 tests/build-and-test.mjs 的 OCR-01 直接断言「四阶行列式不被截成 2×2」；OCR-05 断言提示词里必须还有「不是尺寸模板」这句话
教训 示例的尺寸会被模型当成规范。给视觉模型的 JSON 示例，要么尺寸与常见题一致，要么显式声明「示例仅示范格式」

12. 安全与隐私

  • 计算不出网：所有矩阵运算在本地完成，没有任何上传结果的路径；
  • 唯一外发：OCR 时上传用户主动选择的图片（base64）到用户自己配置的服务商；
  • 密钥：仅存本机 localStorage，不走任何中转；但为明文，公用设备需谨慎；

  • 无账号体系：userId 固定为 guest，不存在登录态泄露面。

附录 B：用 Python 交叉核对期望值

自动化校验的核心是用独立实现复算，避免「从程序输出反推期望值」。

from fractions import Fraction as F

def rref(M):
    M = [[F(x) for x in r] for r in M]
    rows, cols, r, piv = len(M), len(M[0]), 0, []
    for c in range(cols):
        p = next((k for k in range(r, rows) if M[k][c] != 0), None)
        if p is None: continue
        M[r], M[p] = M[p], M[r]
        pv = M[r][c]
        M[r] = [x / pv for x in M[r]]
        for k in range(rows):
            if k != r and M[k][c] != 0:
                f = M[k][c]
                M[k] = [a - f * b for a, b in zip(M[k], M[r])]
        piv.append(c); r += 1
        if r == rows: break
    return M, piv

print(rref([[1,2,3],[4,5,6],[7,8,9]]))
# 期望: [[1,0,-1],[0,1,2],[0,0,0]], 主元列 [0,1]

8.1 无解时增广矩阵秩错误（原 L13）

matrix-ops.ts 原实现：

const { rref: rrefMat, rank: rankAb, pivotCols, steps } = rref(augmented, 1);
const rankA = pivotCols.length;

rref(augmented, 1) 只在系数列选主元，返回的 rank 恒等于 rankA，于是无解分支打印「系数矩阵秩 = 1，增广矩阵秩 = 1，秩不相等」。

修复：

const { rref: rrefMat, pivotCols, steps } = rref(augmented, 1);
const rankA = pivotCols.length;
// 增广矩阵的秩 = 行最简形中非零行的行数（行变换不改变行空间维数）
const rankAb = rrefMat.reduce((acc, row) => acc + (row.some((v) => !v.isZero()) ? 1 : 0), 0);

比"用 rankA + 1"更稳：不依赖"无解 ⇒ 秩恰好多 1"的推理，直接算出来。

  • 用 AbortController + setTimeout 控制 signal，在 finally 里 clearTimeout；
  • 捕获 DOMException 且 name === "AbortError" 时抛出「识别超时（45 秒无响应），请检查网络或更换模型接口」。

1. 关于"把 API Key 存在本地"：cookie 是错的工具

你的意图是对的——Key 只存在用户自己的设备上，不上传。但实现手段不该是 cookie：

维度 Cookie localStorage（当前实现）
会被发送到服务器 每一次同源请求都会带上 不会
托管在 GitHub Pages 时 你的 Key 会被塞进发往 *.github.io 的每个请求头，进入 CDN 日志 完全不发出去
能否 HttpOnly / 防脚本读 前端写不了 HttpOnly；能被 JS 读，防不住 XSS 同样能被 JS 读，但至少不外发
容量 4 KB 5 MB 级
iOS Safari 生命周期 ITP 对 JS 写入的 cookie 有 7 天上限 普通标签页同样有 7 天规则；添加到主屏幕后不受限
适用语义 会话/鉴权状态（服务端需要读） 纯客户端配置

所以现在这套存储方案就是对的：scopedStorage（底层 localStorage），键名带应用前缀，密钥只在本机、不外发。

iOS 上的关键事实（WebKit 官方文档）：

  • Safari 标签页里的脚本存储，7 个"使用日"无交互就被清空 → 用户一周不用就要重填 Key；
  • 添加到主屏幕的 Web App 使用独立存储桶，且豁免这个 7 天清理；
  • 主屏 Web App 的存储与 Safari 相互隔离（不共享）。

结论：引导用户"添加到主屏幕"不只是为了图标好看，它直接决定配置会不会丢。

如果以后要更强的保护，正确方向不是换 cookie，而是：可选口令加密（PBKDF2 + AES-GCM）→ 系统钥匙串（原生壳）→ 服务端代理（Key 不下发）。详见《可行性-视觉模型配置存储》。

  • 免费 Apple ID 的限制：证书 7 天过期、同时最多 3 个自签应用、每周有 App ID 数量上限、不能推送、不能内购。iOS 16+ 安装自签应用还必须先在「设置 → 隐私与安全性 → 开发者模式」里打开开发者模式。

2.1 为什么 A 排第一

这个应用是纯前端、零后端、单页，正好是 PWA 的最佳场景：

  • 计算全部本地完成，离线只是"缓存一份 HTML/JS"，没有同步难题；
  • 没有账号体系，不需要原生能力（相机通过 <input capture> 调系统相机，PWA 同样可用）；
  • iOS 26 起，添加到主屏幕的站点默认以 Web App 形式打开（可关闭），体验接近原生；
  • 关键利好：主屏幕 Web App 的一级域名豁免 ITP 的 7 天清理，数据（包括你的 OCR 配置）不会被 Safari 定期抹掉——而"直接放书签里用"就会被抹。这一条直接决定了本项目在 iOS 上应该走 PWA 而不是"用 Safari 打开一个 HTML"。

PWA 的代价：必须有 HTTPS 托管（Service Worker 只在 HTTPS 或 localhost 下注册），也就是不能靠"发个 HTML 文件给对方"在 iPhone 上用。这与安卓 APK 的分发习惯不同。

2.2 路线 B 的具体做法（零成本、真原生）

关键认知：Sideloadly 这类 Windows 工具能"签名"，但不能"编译"。 所以要把编译放到云上、把签名留在本机。

GitHub Actions (macos-14/15 runner)
  ├─ npm ci / 构建 web 产物
  ├─ npx cap add ios        # 在 macOS 上生成 ios/ 工程
  ├─ npx cap sync ios
  ├─ xcodebuild archive ... CODE_SIGNING_ALLOWED=NO
  └─ 打包成 Payload/App.app → 未签名 .ipa 作为 artifact

Windows 本机
  ├─ 下载未签名 .ipa
  ├─ Sideloadly 用免费 Apple ID 签名并安装（USB）
  ├─ iPhone：设置 → 通用 → VPN 与设备管理 → 信任
  └─ 每 7 天重签一次（或让 AltServer 在同 Wi-Fi 下自动续签）

要点与坑：

  1. 必须在 CI 里生成 ios/：Windows 上 cap add ios 因缺 CocoaPods 失败。要么把 ios/ 提交进仓库（CI 直接 cap sync），要么每次构建都重新 cap add ios（慢但不用维护原生工程）。
  2. 不要提交签名材料：.p12、.mobileprovision 放 GitHub Secrets，或干脆不签（走 Sideloadly 本机签）。本项目没有复杂原生依赖，未签名构建足够。
  3. Info.plist 补相机用途说明：NSCameraUsageDescription。用 <input type="file" capture> 调系统相机通常不弹权限框，但一旦后续改用 getUserMedia 就会崩，提前写好更稳。
  4. 免费证书 7 天到期是硬限制，不是配置问题。要么接受每周插一次线，要么上付费账号。
  5. 私有仓库的 macOS runner 按分钟计费（参考 $0.062/分钟，一次 iOS 构建约 8–15 分钟）；公开仓库免费，但代码会公开。

2.3 路线 C / D 什么时候才值得

  • 要给别人用（TestFlight 内测、上架）：必须付费账号，且需要走 App Store Connect；内部测试可免 Beta 审核，但仍要账号与构建上传。
  • 要做原生能力（钥匙串、后台任务、推送、性能调优）或需要调试器看崩溃：租 Mac 按天最划算，不必买。

可行性分析：网页端保存视觉模型配置

结论先行：技术上完全可行，而且已经实现了——配置写在 localStorage，键名带应用前缀，读写全程 try/catch 包裹。 真正需要判断的不是"能不能存"，而是"存成什么样、在哪些场景会丢、被谁看到"。本文给出选型对比、威胁模型和一份分优先级的改造清单。

1. 现状：现在是怎么存的

项目 实现
存储介质 localStorage（同步、字符串键值）
键名 __miaoda_<appId>__: + __app_linalg_ocr_config
值 JSON：{"baseUrl":"…","apiKey":"sk-…","model":"gpt-4o-mini"} 明文
写入 点「保存配置」时整体覆盖；三项 trim 后存
读取 弹窗打开时回填；识别前再读一次，缺字段直接报「OCR 配置不完整」
清除 「清除配置」立即执行，无二次确认
异常处理 读写失败只 console.error，界面无提示（满配额/隐私模式时可能"看起来保存了，其实没存"）
隔离粒度 同源 + 同浏览器 profile + 同设备；不随浏览器账号同步

顺带确认两件已做的事：API Key 输入框是 type="password"（不明文回显）、界面明确写了"仅保存在浏览器本地，不会上传到任何第三方"。

2. 技术可行性的四条硬约束

约束 具体表现 对本项目的影响
同源隔离 file://、http://127.0.0.1、https://你的域名 是三个不同的源 把 HTML 换个路径/换个打开方式，配置就"消失"（不是丢了，是读不到另一个源的库）
容量 通常 5 MB 级/源，够存几十万条这样的配置 不是问题
生命周期 用户清缓存、隐私模式、浏览器重装、Safari 的 7 天规则都会清掉 需要"配置可迁移"（导出/导入），否则每次重配 Key
不跨设备 浏览器不同步 localStorage 换手机/换电脑必须重填

2.1 Safari / iOS 的关键细节（容易踩）

  • Safari 的 ITP 会删除脚本可写存储（localStorage、IndexedDB、Service Worker 缓存等）在「7 个 Safari 使用日无交互」之后；
  • 豁免：添加到主屏幕的 Web App 使用独立存储桶，其一级域名不受这个 7 天上限约束；
  • 结论：在 iPhone 上用 Safari 标签页打开网页版 → 一周不用就要重配 Key；添加到主屏幕后不会。 这条直接影响 iOS 端的形态选择（见《可行性-iOS端.md》）。

2.2 file:// 的两个不确定性

  • 有的浏览器把每个本地文件当独立源，有的把整个 file:// 当一个源——跨浏览器不一致，同一份 HTML 换个文件名可能就读不到旧配置；
  • crypto.subtle（Web Crypto）在部分浏览器的非安全上下文里不可用。所以任何加密方案都必须先判断 window.isSecureContext，不能假设 file:// 一定有。

3. 存储方案对比

方案 容量 持久性 加密 跨设备 实现成本 适用
localStorage（现状） ~5 MB 中（可被清） 无 ❌ 已实现 个人机、单人使用
sessionStorage ~5 MB 关标签即失 无 ❌ 低 公用电脑、临时演示
IndexedDB 大（按磁盘配额） 中 无 ❌ 中 需要存多套配置/历史
Cookie（document.cookie） 4 KB 中；ITP 对其也有 7 天限制 无；不能设 HttpOnly ❌ 低 无优势，不推荐
Web Crypto + 口令加密后存 localStorage ~5 MB 中 ✅ AES-GCM（口令派生） ❌ 中 有他人共用设备的风险
Credential Management API（存进浏览器密码管理器） — 由密码管理器决定 ✅ 系统级 随浏览器账号同步（若开启） 中 Chrome/Edge；Safari 支持有限
Capacitor Keychain / Keystore（原生壳） — 高 ✅ 系统钥匙串 ❌ 中（需原生插件） APK / 未来的 iOS 壳
服务端代理（云函数持有 Key） — 高 ✅（Key 不下发） ✅ 高（要后端 + 限额 + 鉴权） 要给别人用、或要求"打开即用"

一句话：明文 localStorage 是"够用且诚实"的方案；要更强只有两条路——本机加密（提高门槛，不解决"同机他人已登录"）或服务端代理（真正把 Key 从客户端拿掉）。

4. 威胁模型：谁可能看到这个 Key

威胁 现实可行性 现状 缓解
同一台电脑的其他人打开浏览器 高（F12 → Application → Local Storage，5 秒） 无防护 口令加密 / 系统钥匙串 / 用独立浏览器 profile
恶意浏览器扩展读所有站点存储 中 无防护 减少装扩展；或用独立 profile
页面被注入脚本（XSS） 低（无用户 HTML 注入、无第三方脚本；仅字体 CSS 从 CDN 加载） 无防护 保持不引入外部脚本；CSP 可选

浏览器备份/迁移工具 低-中 随 profile 一起被复制 口令加密
服务商侧日志 取决于服务商 Key 随请求头发给对方 选可信服务商；定期轮换；设置额度上限

要明确的一点：把 Key 硬编码进 HTML 再分发，等于公开。任何"下载即用、不用配置"的方案，都必须是服务端代理 + 鉴权 + 限额，不存在纯前端的优雅解。

5. 建议方案（按投入分级）

P0：不改架构，只补三个缺口（半天）

  1. 保存失败要能看见：localStorage 抛异常（配额满、隐私模式）时，现在只写 console。改成界面提示「配置未能保存（浏览器禁止本地存储）」。
  2. 清除配置加二次确认：误点一次就要重填 Key，成本不对等。
  3. 导出 / 导入配置：一段 JSON 文本（或二维码），换设备时不用重新申请。 js // 导出（不含提示信息，纯配置） const cfg = JSON.parse(localStorage.getItem(KEY) || '{}'); const text = JSON.stringify(cfg, null, 2); // 导入：校验字段齐全 + 类型正确后再写，避免写进脏数据

P1：加一层口令加密（1 天）

适用：电脑可能被他人使用，但不想上后端。

// 概念示意：PBKDF2 派生密钥 → AES-GCM 加密 → 存密文
async function seal(plain, pass) {
  if (!window.isSecureContext) throw new Error('当前环境不支持加密存储');
  const enc = new TextEncoder();
  const salt = crypto.getRandomValues(new Uint8Array(16));
  const iv   = crypto.getRandomValues(new Uint8Array(12));
  const base = await crypto.subtle.importKey('raw', enc.encode(pass), 'PBKDF2', false, ['deriveKey']);
  const key  = await crypto.subtle.deriveKey(
    { name: 'PBKDF2', salt, iterations: 310000, hash: 'SHA-256' },
    base, { name: 'AES-GCM', length: 256 }, false, ['encrypt']
  );
  const ct = await crypto.subtle.encrypt({ name: 'AES-GCM', iv }, key, enc.encode(plain));
  return { v: 1, salt: [...salt], iv: [...iv], ct: [...new Uint8Array(ct)] };
}

要点：

  • 口令不落盘，只在解锁时输入；忘记口令 = 配置作废（要能接受）；
  • 每次唤醒需解密（弹窗打开时），别把明文缓存在内存全局变量里长期驻留；
  • file:// 下若 crypto.subtle 不可用，退化为要么不加密、要么要求用 https/localhost 打开。

P2：把 Key 移出客户端（1–2 天，需后端）


前端 → 你的云函数（带一次性/短期 token） → 模型服务商（Key 在服务端环境变量）
  • 前端只存"会话票据"，泄露也只能用很短时间；
  • 可在服务端加每日次数/额度上限、按用户限流；
  • 适合"要发给同学用"的场景——否则每个人都得自己申请 Key，这是当前最大的使用门槛。

不建议做的

做法 为什么不做
Base64 / 自定义异或"混淆"后存 只是拖延 10 秒，反而给人"已加密"的错觉
把 Key 写进 HTML 等于公开分发密钥
把 Key 存 Cookie 4 KB 限制、无 HttpOnly、仍受 ITP，越改越差
存到 URL 参数里 会进历史记录、Referer、截图，泄露面更大
